1. OBJECTIVE
Implement a secure, scalable, production-ready mobile OTP authentication system for DharmaDarshan.
The authentication module must support:
* New customer registration using mobile OTP.
* Existing customer login using mobile OTP.
* Automatic customer identification.
* OTP generation, delivery, verification and expiration.
* Resend OTP functionality.
* OTP attempt restrictions.
* Rate limiting and abuse prevention.
* Access and refresh token management.
* Multiple-device session management.
* Logout and logout from all devices.
* Account status validation.
* Mobile number change with OTP verification.
* Authentication audit logging.
The implementation must be reusable across customer, astrologer and other approved user roles.

3. AUTHENTICATION USER FLOW
3.1 New Customer
1. Customer opens DharmaDarshan.
2. Selects Login / Continue.
3. Enters mobile number and country code.
4. Frontend validates the number.
5. Backend validates the request.
6. Backend generates OTP.
7. OTP is sent through the configured SMS provider.
8. Customer enters OTP.
9. Backend verifies OTP.
10. Backend checks whether the customer exists.
11. If the customer does not exist, create a new customer record.
12. Assign the default USER role.
13. Mark the mobile number as verified.
14. Create an authenticated session.
15. Generate access and refresh tokens.
16. Return customer details.
17. Navigate to the customer home screen.
3.2 Existing Customer
1. Customer enters registered mobile number.
2. Backend generates and sends OTP.
3. Customer enters OTP.
4. Backend verifies OTP.
5. Identify the existing customer.
6. Validate customer account status.
7. Create a new device session.
8. Generate access and refresh tokens.
9. Return customer information.
10. Navigate to the home screen.
3.3 Authentication Flow Rules
* Do not require customers to register separately before OTP login.
* Existing customer records must never be duplicated.
* Use normalized E.164 mobile numbers.
* New customers must receive the default USER role.
* Do not allow role selection through the public login API.
* OTP must be generated and verified exclusively by the backend.
* Successful OTP verification must consume the OTP.
* Previous OTPs must become invalid when a replacement OTP is issued.

7.1 Send OTP
POST /send-otp
Request:
{
"phoneNumber": "+919876543210",
"countryCode": "+91",
"purpose": "LOGIN",
"channel": "SMS"
}
Backend operations:
1. Validate request.
2. Normalize phone number.
3. Apply IP and phone-number rate limits.
4. Check account eligibility.
5. Generate six-digit OTP.
6. Generate unique challenge ID.
7. Generate keyed OTP hash.
8. Persist challenge.
9. Invalidate previous active challenge for the same purpose and number.
10. Send OTP using configured SMS provider.
11. Return challenge metadata.
Response:
{
"success": true,
"message": "OTP sent successfully",
"data": {
"challengeId": "challenge-uuid",
"maskedPhoneNumber": "+91******3210",
"otpLength": 4,
"expiresIn": 300,
"resendAfter": 90
  }
}
Never return OTP in API responses.
Use a generic response policy that does not reveal whether the phone number belongs to an existing customer.

13. Create session.
14. Generate access token.
15. Generate refresh token.

7.3 Resend OTP
POST /resend-otp
Request:
{
"challengeId": "challenge-uuid"
}
Validations:
* Challenge must exist.
* Challenge must be eligible for resend.
* Resend cooldown must have elapsed.
* Resend limit must not be exceeded.
* Challenge must not already be consumed.
* New OTP must be generated.
* Previous OTP must become invalid.

Operations:
* Validate refresh token.
* Verify session status.
* Verify token expiration.
* Rotate refresh token.
* Store new token hash.
* Invalidate previous token.
* Return new access and refresh tokens.
Refresh-token reuse must trigger revocation of the affected token family and a security audit event.

8. OTP VALIDATION AND SECURITY RULES
Initial configuration:
ParameterValueOTP digits4OTP validity5 minutesResend cooldown90 secondsVerification attempts5 per challengePhone OTP request limit5 per hourIP OTP request limit10 per hourAccess token validity15 minutesRefresh token validity30 days
These values must be environment-configurable.
Additional security requirements:
1. Use cryptographically secure random OTP generation.
2. Store only keyed OTP hashes.
3. Never store OTP plaintext.
4. Never return OTP in production responses.
5. Never log OTP.
6. Invalidate previous OTP after resend.
7. Consume OTP exactly once.
8. Enforce attempt limits atomically.
9. Apply IP and phone-based rate limiting.
10. Use HTTPS exclusively.
11. Validate JWT signature, issuer, audience and expiration.
12. Rotate refresh tokens.
13. Detect refresh-token reuse.
14. Protect against concurrent verification requests.
15. Prevent customer ID manipulation.
16. Prevent unauthorized role assignment.
17. Avoid account enumeration through login responses.
18. Implement audit logging and retention policies.
For OTP hashing, use HMAC-SHA-256 with a server-side secret and challenge-specific context.
For refresh tokens, use high-entropy cryptographically random opaque tokens.
